## Hardware floors and what can be bounded now

### Memory-model derivation (inferred bound)

The collected FireSim run is `f2_gemmini_rocket_ddr3llc_60mhz` (`runs/perfX/fpga/zF2-resnet-trace-buffered-20261027/meta.json`). The published FireSim/Chipyard defaults describe a 64-bit memory bus clocked at 1 GHz and a FASED DDR3-2133 timing model; the 64-bit path therefore has a **nominal transfer ceiling 8 GB/s**. At 60 MHz target clock this is 133.33 bytes/target-cycle, so a perfect-row-hit bandwidth-only lower bound is bytes / 133.33. This derives from the interface clock/width, not DDR3-2133 DIMM peak. The FASED model adds timing constraints; FR-FCFS and LLC behavior, row misses, refresh, contention, and access latency reduce sustained throughput. Public FireSim discussion also reports that 1 GHz x 64 bits implies 8 GB/s despite DDR3-2133 timing values ([FireSim memory-bandwidth discussion](https://groups.google.com/g/firesim/c/t6XhTGltdPI)); Chipyard describes the default FASED model and its configurable DDR3 FR-FCFS/LLC composition ([Chipyard FPGA-accelerated simulation docs](https://chipyard.readthedocs.io/en/1.12.3/Simulation/FPGA-Accelerated-Simulation.html)). This does not use measured per-run DRAM beat counts: collected `memory_stats0.csv` contains only the header, so there is no measured bandwidth result.

### ResNet-50 (INT8 Gemmini matmul trace)

Measured: 2,088,249,127 FireSim invoke cycles. From the 54 logged Gemmini dispatch shapes in `runs/perfX/results/resnet/firesim-trace.json`, total useful work = 4,089,184,256 MACs. Compute-only ideal = 4,089,184,256 / 256 = **15,973,376 cycles** (0.266 s), 130.7x below observed. Overall useful MAC rate is 1.96 MAC/cycle = 0.765% of the stated 256 peak; Gemmini-only is 2.48 MAC/cycle = 0.966% of peak.

Traffic estimate from those dispatch shapes (one pass per logged matmul, INT8 LHS/RHS): 25,502,912 bytes of RHS weights + 21,816,064 bytes of LHS activations = **47,318,976 compulsory operand bytes**; at nominal 8 GB/s, **354,892 cycles**. If every output is pessimistically charged as a 4-byte accumulator write, another 44,459,936 bytes gives 91,778,912 bytes / **688,342 cycles**. The former omits output stores and intermediate reloads, so is a compulsory lower estimate under the trace’s one-pass assumption; the latter is a simple traffic upper estimate, not a DRAM requirement because LLC reuse and output requantization affect actual traffic. Either is far below the observed invoke time. Per-run DDR byte counts are not present.

Measured cycle split in `firesim-trace.json`: Rocket scalar dispatches 405,606,163 cycles, Gemmini dispatches 1,653,621,540 cycles, unattributed 29,021,424. The 15.97M pure MAC floor leaves a very large accelerator-side difference. That difference is **not inherently hardware floor**: the user-provided optAnalysis evidence attributes 57.75% of invoke to scalar requantization epilogues inside Gemmini dispatches; 14.3% to M=49 tiny tiles; 8% scalar im2col/packing; and 6.2% maxpool+quantize. These values are in `runs/optAnalysis/REPORT.md` (reported from analysis, not independently regenerated here). M=49 on a 16-row systolic tile has at most 49/ceil(49/16)*16 = **76.56% row efficiency** for that dimension; combined M/N/K tails further reduce useful MAC rate. The actual algorithmic MAC count already excludes padded MACs, so 15.97M remains a valid ideal arithmetic bound; the padding ceiling describes achievable tile issue efficiency, not extra useful work.

Classification: scalar requantization and scalar packing costs are measured in this binary but not irreducible hardware costs: software/compiler/plugin mapping (M/O) can change them. Rocket’s in-order scalar-only path is an H constraint for operations left there, but the trace does not establish those operations must stay there. DIM16 tails and finite Gemmini throughput are H ceilings; current severe underutilization and small-tile frequency are additionally mapping/scheduling choices (M/O). The traffic lower bound is H bandwidth capacity, while real measured DRAM traffic is unknown.

### TinyLlama

Available measurement is Spike only: 4,751,696,797 *functional simulator cycles*, not FireSim cycles (`runs/perfTL/results/tinyllama/spike-trace.json`). It logs 15,502,147,584 estimated Gemmini MACs, giving a Gemmini-only arithmetic floor **60,555,264 target cycles** at 256 MAC/cycle. The measured Spike trace also reports 4,331,009,607 scalar dispatch simulator cycles; neither quantity is physical Rocket timing. FireSim plain and instrumented cycles are explicitly `not yet measured` in `runs/perfTL/results/summary.md`.

The known FP32 lm_head shape is 16 x 32000 x 2048 (from the user’s prior trace summary and trace dispatch catalog): 1,048,576,000 MACs. On a scalar FPU, an ideal pipelined `fmadd.s` issue rate of one independent instruction/cycle gives a **conditional 1.049B-cycle** lower bound (one FMA per MAC); dependent accumulation chains would be slower according to FMA latency. This is a microarchitectural inference, not a measured Rocket CPI. The target-specific Rocket FPU implementation/latency and a TinyLlama FireSim dispatch trace are not included in local result artifacts. The model cannot yet receive an end-to-end measured-vs-floor gap number. We should not label the huge scalar lm_head as unavoidable from hardware: it is scalar in this export, and using Gemmini or another supported compute unit would change the mapping if the exactness/export constraints allow it (O/M).

### SmolVLA

Available execution evidence is `runs/smB/full-summary.json`: 430,334,661,263 estimated instructions from an **altered WG0-only computation**, explicitly marked there as approximate scaling, not full model execution or acceptance. It is not a cycle count. User-provided `runs/probeSPL`/`runs/smB` breakdown identifies approximately 102B FP32 QK MACs + 88B and 88B FP32 PV MACs that run scalar, plus 62B patch-convolution MACs. Conditional scalar FMA issue lower bound for the 278B FP32 attention MACs is **278B cycles** at one independent FMA/cycle; that is the main hard hardware throughput floor only if these FP32 operations remain on Rocket. Moving or quantizing them changes the model/software contract, so the current exactness and export choices are O constraints. Patch convolution’s 62B MACs would have 242.2M compute-only Gemmini cycles at 256 MAC/cycle, if all work maps efficiently; no full measured Gemmini MAC/FireSim count exists. No defensible full-model data-movement floor can be reported without authoritative full shape/weight byte totals and measured/export execution counts. `runs/perfX/REPORT.md` says SmolVLA FireSim handoff did not produce UART/results; no model-level hardware cycles are present.

## Rocket scalar floor: scope and caveat

A one-independent-FMA-per-cycle ceiling is a best-case issue-rate assumption for a pipelined FPU, giving one scalar instruction/MAC. It is not a complete CPI model. A true dependent reduction has recurrence latency, and loads have address/availability constraints; without the exact Rocket FPU parameterization and compiled instruction schedule, assigning an exact `fmadd.s` latency or CPI would be false precision. The attempted calibration requires paired FireSim and Spike per-dispatch instruction counts. ResNet has paired dispatch cycles but not instruction counts in its CSV/JSON; Spike `cycles` are functional-simulator cycles, so their scalar ratio (1.88x for matching scalar dispatches) is not an instruction CPI calibration. TinyLlama lacks FireSim results. No timing microbenchmark was run because Spike is not a timing simulator, and no model workload was rerun.
