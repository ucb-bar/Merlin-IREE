# TinyLlama and smolVLA sink classification (attT)

Updated 2026-10-27 UTC. Read-only investigation; all new files are in `runs/attT/` except the requested shared first-result handoff `runs/probeSUMMARY/attT.txt`. No model was rebuilt or rerun here. Required reports were read first. No tolerances changed. Existing exactness gates remain TinyLlama `atol=rtol=1e-3` (TinyLlama REPORT) and smolVLA `atol=rtol=1e-3` for compiler/reference (SPEC); smB's materialization correctness was checked bitwise. Class labels refer to the primary cause; mixed causes are identified.

## Classification

| Sink | Class | Evidence and confidence |
|---|---|---|
| TinyLlama FP32 `lm_head` (81.5% of Spike cycles) | **O primary; M secondary; H contributes** | **MEASURED:** `runs/perfTL/results/tinyllama/spike-trace.csv` attributes 3.87G/4.75G cycles to scalar FP32 `batch_matmul_1x16x32000x2048`; TinyLlama export report says 154 decoder linears are INT8, while the explicit exporter filter skips `lm_head`. **INFERRED from code:** that skip is export policy, not an upstream IREE inability to represent FP32; the scalar lowering is poor for this shape. The Merlin Gemmini named matcher only takes rank-2 i8*i8->i32 or optional rank-2 FP8, and does not accept FP32/rank-3 batch matmul (`iree-latest/source/Merlin-IREE/compiler/src/merlin/Dialect/Gemmini/Transforms/ConvertToGemmini.cpp:433-460`; qx audit). INT8 head variant is pending in `runs/tlHead/REPORT.md`; there is no result to claim quantization accuracy or speed. Rocket has no vector unit, a hardware constraint on native FP32 throughput.
| TinyLlama FP32 attention (1.7%) | **O/M primarily; H secondary** | **MEASURED:** Spike trace classification says FP32 scalar attention, ~1.7% of cycles (source handoff context; row-level trace in perfTL CSV). **INFERRED:** graph remains FP32 because export quantizes selected `Linear`s only; upstream has quantized batch-matmul lowering for already-quantized IR, but no auto-quantization/calibration pass. Merlin Gemmini is rank-2 integer/optional FP8 and rejects FP32 batch matmul (same source lines; qx report). No quantized attention recipe is validated; quantization is not a compiler flag.
| TinyLlama elementwise (8%) | **O/U mixed, measured attribution unavailable** | **MEASURED:** 8% scalar elementwise in supplied TinyLlama profile. **NOT MEASURED in this task:** a paired plain-vs-exact-rewrite instructions/element run. Therefore exactness recipes cannot be blamed from this percentage alone. Scalar-only Rocket is an H ceiling; upstream CPU loop/codegen quality may contribute (U), and any extra exactness lowering may contribute (O), but split is unproven.
| smolVLA FP32 QK/PV attention | **O export/representation + M admission; U codegen; H** | **MEASURED:** baseline QK batch-matmul is 102.483G instructions (288 calls); smB post-materialization QK is 102.543G. Post-rewrite PV scalar groups cost 88.212G + 88.121G; complete residual attention/projection work leaves whole estimate 430.335G (`runs/smB/full-comparison.md`, `runs/smB/REPORT.md`). **INFERRED:** exporter left these ops FP32; Merlin matcher rejects FP32 and rank-3 batch matmul, while upstream supports lowering pre-quantized batch matmul, not selecting quantization. PT2E/TorchAO routes are not a ready Gemmini recipe and tested eager INT8 variants fail the declared max-error gate (`runs/sq1/REPORT.md`, `runs/sq3/REPORT.md`). Scalar codegen on RV64 and Rocket hardware limit throughput. Primary actionable cause is O representation plus M pattern gap; labeling it solely U would be wrong.
| smolVLA patch conv/projections left FP32 | **O recipe + M Gemmini type/layout gate; U scalar codegen; H** | **MEASURED:** three `elementwise_786432_f32` camera projection dispatches cost 61.687G before; rewritten broadcast form costs 61.667G (`runs/smB/full-comparison.md`). SPL baseline counts patch projection at ~61.69G. **INFERRED:** exporter quantizes linears, not Conv2d; plugin Conv matcher expects rank-3 i8 input, rank-4 i8 filter, rank-3 i32 output plus recognized maps (`runs/qx/REPORT.md`; source `.../ConvertToGemmini.cpp:542-574`). No INT8 patch-conv candidate has passed accuracy; SQ2 is explicitly not evaluated (`runs/sq2/REPORT.md`). Scalar code quality and Rocket scalar hardware explain cost after leaving it FP32.
| FP32 scalar matmul/code quality (3–3.5 instructions/MAC; patch projection ~34 instr/MAC) | **U codegen primary; H throughput; evidence not sufficient for a microkernel verdict** | **MEASURED:** smB materialization changes dispatch boundaries but QK instructions stay essentially flat, 102.483G ->102.543G; thus this rewrite does not improve matmul codegen. Supplied smolVLA baseline analysis reports ~3–3.5 instructions/MAC and patch conv ~34 instr/MAC; TinyLlama scalar lm_head trace is corroborating end-to-end cost. This is evidence of emitted scalar code cost, not yet a paired upstream-options experiment. **INFERRED:** RV64 scalar LLVM CPU lowering is inefficient versus hand-unrolled FMA expectation; no supported vector unit on Rocket is H. I did not establish that `--iree-opt-data-tiling`, `--iree-llvmcpu-enable-ukernels=all`, or tile flags improve RV64 Spike instructions/MAC. User-requested option sweep and direct ideal-kernel comparison remain unrun; do not present them as measured.
| smolVLA exactness rewrites (exact-exp, ordered means, integer RoPE) | **O suspected contributor; impact not isolated** | **MEASURED:** smB exact materialization rewrite removes redundant max-reduction recomputation: `elementwise_1572864_f32` falls from 2.802T to zero; replacement max/exp work is explicitly counted, and full estimate improves 3.488T ->430.335G (8.106x), with host output bitwise equal to protected CPU/PyTorch goldens. However this is dispatch-materialization/recomputation, not a paired plain-exp vs exact-exp comparison. `runs/fixE/REPORT.md` / `runs/fixG/REPORT.md` document exactness implementation, but no same-input plain-vs-recipe per-element instruction delta was produced in this investigation. So exactness is demonstrably expensive only where the trace exposes it; attribution to ordered mean/RoPE or extra exact-exp instructions/element is **not resolved**.
| smolVLA softmax O(N^2) recomputation / fusion | **O graph/dispatch formation primary** | **MEASURED:** SPL estimates 2.802T in repeated max+exp consumer kernels; after barriers/materialization the corresponding group is removed, full scaled estimate 3.488T ->430.335G, and complete attention block 23.059G ->2.094G. Host full output is bitwise equal; exact-recipe Spike slices are bitwise equal. This experimentally establishes duplicated reductions caused by generated dispatch structure and that materializing shared intermediates fixes them. **INFERRED:** whether root responsibility is exporter graph, upstream dispatch formation/fusion, or Merlin preprocessing flags is not isolated; no matched upstream-vs-Merlin flag compile was performed. Class O is the observed repair locus, with U/M ownership unresolved.
| Gemmini matmul/conv throughput limits | **H** for fixed hardware ceilings; **M/O** for missing coverage | **MEASURED:** integer INT8 matmuls are present in Gemmini traces; FP32 sinks remain scalar. **INFERRED from code:** default DIM16 array, 8-bit operands and plugin's narrow type/rank patterns preclude these FP32 batch matmuls/patch convs. Hardware facts supplied: DIM16, Rocket without vector, DDR3/FR-FCFS + LLC at 60 MHz. These limits cap throughput but do not explain why export chose FP32 or why scalar loop code has its instruction count.

## Measured vs inferred summary

Measured: TinyLlama FP32 output head dominates at 81.5%; its INT8 export filter excludes the head; smolVLA residual QK/PV/projection counts; the exact materialization rewrite removes repeated max/exp work while preserving host numerical output bitwise; candidate quantization routes have failed or remain unevaluated under fixed gates. Code-based inference: no auto-quantization facility covers FP32 attention/conv; Gemmini rejects these types/ranks; scalar CPU lowering and Rocket hardware make remaining FP32 work slow. Not measured here: bundled-vs-merged compiler option sweep for data tiling/ukernels, hand-written ideal scalar kernel, paired exactness recipes vs plain lowering per-element, TinyLlama INT8-head result, or responsibility split for O(N^2) dispatch formation among upstream/Merlin/export flags.
